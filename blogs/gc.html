GC Tuning Is Not About the GC

Hard-won operational understanding from backend infrastructure, distributed systems, performance engineering and production reliability.

JVMPerformanceGarbage CollectionProfiling

Start with allocation behavior

Long or unpredictable pauses are often allocation problems in disguise. Before changing collector flags, understand what the application allocates, where it allocates and which objects survive.

Profile first

JFR and async-profiler can reveal allocation hot spots, retention paths, humongous objects and CPU profiles without turning tuning into guesswork.

Collector choice is a trade-off

Moving from G1 to ZGC can reduce latency at the cost of memory headroom and operational complexity. Object pooling can help on a proven hot path, but it introduces lifecycle and reset-bug risks.

Measure the live set

A smaller live set gives the collector less work. Retention bugs, oversized buffers and accidental object graphs can be more consequential than any individual GC flag.

Treat upgrades as experiments

Collector tuning is not permanent. JVM upgrades, workload changes and container limits can alter behavior. Re-profile after major changes instead of assuming yesterday's numbers remain valid.

Good architecture makes correctness obvious, failure modes explicit, performance measurable and operations boring.
