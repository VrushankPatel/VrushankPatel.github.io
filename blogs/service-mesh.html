Why Your Service Mesh Is Slower Than You Think

Hard-won operational understanding from backend infrastructure, distributed systems, performance engineering and production reliability.

Distributed SystemsEnvoyIstioLatency

The latency budget did not disappear

A service can have a clean single-digit millisecond p99, then jump into double digits after sidecar injection even though the application code, CPU allocation and physical network are unchanged. The useful question is where the new latency is actually being spent.

Trace the five-stage path

A request moves from the client application into the client proxy, across the network, through the server proxy and finally into the server application. The network hop is often the least interesting part; user-space proxy work is where connection establishment, routing, telemetry and policy processing accumulate.

The proxy is the expensive part

In a sidecar topology, Envoy executes a filter chain for every request. Metadata exchange, RBAC, rate limiting, scripting, route matching and telemetry all consume CPU. Broad routing configuration can also increase proxy memory and lookup work as the service count grows.

Connection churn changes the economics

mTLS handshakes are expensive when applications repeatedly create short-lived connections. Long-lived HTTP/2 connections amortize cryptographic work across many requests. Connection reuse is often a higher-leverage optimization than changing packet interception rules.

Measure before tuning

Use client-side timing breakdowns, Envoy's upstream-service-time header and the proxy's admin statistics to isolate the cost. Then scope routing configuration, reduce unnecessary telemetry on hot paths and tune connection pools.

When a mesh stops making sense

The overhead compounds across serial service hops. For extremely latency-sensitive workloads, alternatives include eBPF-based routing, Ambient mode or client-side traffic-management libraries. The decision should be driven by the latency budget and operational requirements.

Good architecture makes correctness obvious, failure modes explicit, performance measurable and operations boring.
